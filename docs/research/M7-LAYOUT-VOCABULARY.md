# M7 layout vocabulary research

Read-only primary-source comparison, consulted 2026-08-30. This is a vocabulary study, not a claim that Lucent should implement any source framework's complete algorithm.

ADR 0002 is the subsequent product decision. It preserves the bounded layout names recommended here and replaces `Fill` only because M7 explicitly adopts a real solid/linear-gradient `Brush` contract.

## Lucent baseline (facts)

The existing surface is in `src/Lucent.Core/LayoutScene.cs`: `Arrangement.Axis` (`LayoutAxis.Row|Column`), nullable `Width`/`Height`, finite `MinWidth`/`MinHeight` and `MaxWidth`/`MaxHeight`, `Spacing`, `MainAlignment` and `CrossAlignment` (`Start|Center|End|Stretch`), `Clip`, and `Scroll` (`ScrollOffset`). Visual paint is `SceneProperties.Fill` and inherited `Foreground` in the same file. There is currently no `Padding`, `Opacity`, or `Background` property (the nearest existing paint name is `Fill`). The layout implementation is retained, bounded row/column layout; it is not a CSS-complete flex implementation.

### Important semantic differences

1. **Names that transfer safely:** `Row`/`Column`, `Width`/`Height`, `MinWidth`/`MaxWidth`, `Spacing`, `MainAlignment`/`CrossAlignment`, `Clip`, and `Scroll` are familiar across multiple systems. CSS's `justify-content` and `align-items` are recognizable, but Lucent's existing `MainAlignment`/`CrossAlignment` names better avoid promising CSS free-space, wrapping, auto-margin, writing-mode, or flex-grow behavior.
2. **Do not call `Spacing` `gap` unless semantics are fixed.** CSS `gap` is physical row/column shorthand and can have two axes; GPUI and Slint use `gap`/`spacing` in narrower layout APIs; Avalonia and Qt use `Spacing`/`spacing`. Lucent currently has one axis-relative scalar and no wrapping, so `Spacing` is the least misleading name.
3. **Alignment is not one algorithm.** CSS `justify-content` distributes post-flex free space; Compose `Arrangement` can distribute or space children; Flutter `MainAxisAlignment` distributes remaining space; Qt `Layout.alignment` is an attached child placement flag; Avalonia alignment places a child in an allotted slot. Reusing names without adopting those algorithms is a compatibility trap.
4. **Size semantics differ substantially.** CSS and Compose sizes are negotiated through parent constraints; Flutter's `BoxConstraints` are explicit min/max bounds; Qt uses minimum/preferred/maximum plus fill and ratios; Slint adds preferred sizes and stretch factors; Avalonia's explicit dimensions are constrained by min/max. Lucent's nullable explicit size and finite bounds should remain its own contract.
5. **Paint vocabulary is especially non-portable.** `Background`, `Fill`, `color`, and `background` refer to different object types and ownership. Lucent's existing `Fill` is the narrowest safe name. `Opacity` should not be implied by color alpha: in CSS/GPUI/Compose/Flutter/Slint it can affect a subtree, whereas an alpha paint only affects that paint.
6. **`Clip` is a good bounded boolean name.** CSS overflow modes and Qt/Slint clipping are richer; Lucent's `Clip=true` should not imply scrollability. Scrolling should remain an explicit viewport/state (`Scroll`) as current `Controls.ScrollViewport` does.

## Recommendations (separate from facts)

- **High — semantic compatibility:** `src/Lucent.Core/LayoutScene.cs` should not rename `MainAlignment`/`CrossAlignment` to CSS/Flutter/Compose names without first adopting their free-space algorithms; the same names do not mean the same thing.
- **Medium — scope clarity:** `src/Lucent.Core/LayoutScene.cs` has no `Padding`, `Opacity`, or `Background`; adding aliases now would imply behavior that does not exist. If added later, specify edge-value, subtree-opacity, and paint ownership semantics first.
- **Medium — scrolling contract:** `src/Lucent.Core/LayoutScene.cs`'s explicit `Clip` and `Scroll` split is safer than an `Overflow` alias; CSS `overflow` conflates clipping and scroll-container behavior.
- Keep `Axis`, `Width`, `Height`, `MinWidth`, `MinHeight`, `MaxWidth`, `MaxHeight`, `Spacing`, `MainAlignment`, `CrossAlignment`, `Clip`, and `Scroll`; they are familiar and accurately describe Lucent's bounded vocabulary.
- Keep `MainAlignment`/`CrossAlignment` rather than renaming to CSS `justify-content`/`align-items`; document that `Start|Center|End|Stretch` is a finite Lucent alignment enum, not CSS/Compose/Flutter free-space distribution.
- If padding is added, use `Padding` (a four-edge value), not `Margin`; no padding exists today, so adding it is outside this vocabulary-only task. If opacity is added, use `Opacity` and explicitly define subtree-vs-paint behavior. Preserve `Fill` for the existing paint property; do not alias it to CSS `background`.
- Keep `Scroll` as viewport state rather than introducing `Overflow`; the existing scroll behavior has bounded offsets and retained input semantics, while `overflow` would imply CSS's several clipping/scrolling modes.
- Treat framework algorithms as inspirations only. Add executable contract tests before changing any semantics (especially size clamping, alignment free space, clipping, or scroll extents).

## Gaps

- No primary source was found that establishes a single, cross-framework meaning for `background`, `spacing`, or alignment; the differences are the finding.
- CSS drafts are living specifications and do not have a framework-style release version. Pin a dated W3C snapshot if legal/reproducibility requirements demand one.
- Qt and Slint licensing is edition/module/usage-sensitive; legal review is required before copying code or adding either dependency. This research only records source licenses.
