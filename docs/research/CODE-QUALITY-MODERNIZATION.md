# Modern C# quality modernization

Status: researched policy for the post-M7 maintainability pass

## Current baseline

Lucent already pins .NET SDK 10.0.400 and enables nullable references, implicit usings, warnings as errors, build-time code style, and NativeAOT/trimming analysis for runtime projects. Its `src`/`apps`/`tests` project boundaries are coherent. The main maintainability debt is within those boundaries: several large multi-concern files, no repository formatter, sparse consumer-facing public API documentation, and an analyzer level that follows the installed SDK rather than a frozen rule set.

## Adopted recommendations

1. Pin CSharpier 1.3.0 in the repository-local .NET tool manifest. Use explicit `format` and fail-closed `check` commands; do not adopt `CSharpier.MSBuild`, whose default Debug behavior mutates source during builds. Generated `*.g.cs` and `<auto-generated>` output remains excluded by CSharpier's normal generated-code boundary.
2. Establish one repository-wide CSharpier baseline commit, then require `dotnet csharpier check .`. Keep later semantic changes separate from mass formatting where practical.
3. Pin SDK analysis to `10.0-Recommended`, retain warnings as errors, nullable analysis, platform analysis, and NativeAOT/trimming gates. Do not enable `All`: its low-signal and metrics-oriented rules would create policy churn without evidence. Add rules individually only after measuring their signal.
4. Enable XML documentation generation for author-facing libraries and document public APIs with consumer-oriented summaries. Use `<param>`, `<typeparam>`, `<returns>`, `<exception>`, `<remarks>`, and `<see cref>` when they add real usage or lifecycle information; do not merely restate signatures.
5. Normally keep one primary public type per matching file. Small private helpers and inseparable, compact vocabulary types may remain together. Split large types only at a real concern, generated/authored, or platform boundary; do not create one-implementation interfaces, forwarding wrappers, or speculative layers to satisfy a folder scheme.
6. Use partial classes only for generated/authored halves or a genuinely large type with named concerns such as `Type.Properties.cs` or `Type.Events.cs`. Prefer extracting an independently meaningful type over hiding unrelated responsibilities in partial files.
7. Keep existing executable contract tests and NativeAOT proofs. A conventional test framework is not required until filtering, diagnostics, or parallel execution provides measured value. Format, then build/analyze, then run focused/full contracts.
8. Defer PublicApiAnalyzers, package validation baselines, and broad `[Experimental]` annotation until Lucent has a deliberate shipped API/versioning contract. Pre-1.0 status alone does not justify compatibility machinery.
9. Use `ContinuousIntegrationBuild=true` only in CI. Modern SDK builds are already deterministic; retain locked restores and the pinned SDK as the reproducibility authority.

## Rollout

1. Add and run the pinned formatter; capture one mechanical baseline.
2. Pin `10.0-Recommended`, build warning-clean, and add only narrow measured editor rules.
3. Reorganize the largest source and contract files by existing domain concepts without changing behavior.
4. Enable documentation output project-by-project and complete meaningful docs for public surfaces.
5. Run CSharpier check, warning-clean builds, focused tests, full `Verify-M1`, SDK/parity proofs, and a fresh maintainability review.
