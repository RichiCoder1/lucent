# Application services and negotiated shutdown

Lucent keeps the synchronous desktop entry point on its STA owner while pumping asynchronous application lifecycle work. Core owns one session, composition and owner synchronization context. The optional `Lucent.Hosting` adapter owns a Microsoft Generic Host and one asynchronous application DI scope. Service lookup occurs at the composition root; `.lui` components receive typed models and the session explicitly. No per-element service scopes or service-locator syntax are added.

## Startup and ownership

`Build()` snapshots configuration without starting services. `Run(IApplicationLifecycle)` transfers lifecycle ownership for one run; `Run(ComponentRecipe)` remains the small service-free convenience. The platform installs its wake transport before starting the session. Lucent lifecycle continuations and root creation run through the session context, then Core mounts the returned recipe. Microsoft Generic Host service hooks may run on worker threads; UI ownership belongs to the session and composition, not those service hooks. Startup or platform failures still attempt service stop, composition cleanup and lifecycle disposal, preserving failures from each boundary. A host must continue pumping until the session completes; Core supplies an owner-thread cleanup pump if the platform exits abnormally.

`HostedApplication.CreateBuilder()` returns Microsoft's `HostApplicationBuilder` with defaults disabled, scope validation enabled and an inert desktop `IHostLifetime`. Applications explicitly add configuration sources and logging providers. The adapter invokes `IHost.StartAsync` and `StopAsync`; it never invokes the Generic Host's console event loop. Generic Host stopping notifications request Lucent close and do not skip preparation. Such notifications are irreversible signals, so accepted writes must not use that cancellation token.

## Close preparation is the recovery boundary

A close request starts one `PrepareCloseAsync` operation. Repeated requests coalesce; requests during startup wait for startup. Preparation must stop accepting new writes and await the already accepted work. Return false to decline close, or throw to expose a retryable failure in reactive session status. The composition, window and services remain available; another close request retries preparation. Applications restore write acceptance when declining close if their workflow allows continued editing.

Accepted writes belong to the application service, not to an element's cancellable read scope. Scope disposal may cancel an obsolete read; closing a view must not cancel a save the application has accepted. The framework does not replay writes or provide a persistence queue in this issue. The persistence service will define its ordering, durability and retry semantics separately.

Once preparation succeeds, shutdown is irreversible: stop services, dispose the composition on its owner, then asynchronously dispose the application DI scope and the host. Stop/disposal errors are terminal and aggregated across these boundaries; reopening a partly stopped host would imply capabilities it no longer has. Fatal platform failure bypasses retryable preparation because the host is no longer available; service stop must also finish or report accepted work on that path. No force-close timeout discards accepted work. Service-specific timeouts and recovery belong in preparation; the Generic Host retains its normal terminal-stop timeout policy.

## Fatal failures and reporting

Accepted owner clarification, September 8, 2026. Implementation and regression coverage are tracked in [#124](https://github.com/RichiCoder1/lucent/issues/124).

An unexpected exception escaping an application callback, reactive drain, close preparation or layout/frame boundary ends the application session through terminal cleanup with the original failure preserved. A reporting hook cannot mark the failure handled and resume a potentially inconsistent session. Expected validation, load and save failures remain explicit recoverable application state; close preparation returns false after publishing that state when the request may be retried. Environmental failures such as missing glyphs and renderer resets receive targeted recovery where supported. Component error boundaries require a separate recovery design and are not part of this contract.

Fatal shutdown cancels an in-flight close-preparation flow and proceeds to terminal cleanup without waiting for that preparation to finish. Late preparation completion cannot reopen or otherwise change the terminal session, and late failures must be observed. Cancellation of preparation is separate from ownership of accepted writes: application services must finish or report accepted work during shutdown. This does not authorize a framework timeout that silently discards saves, nor does it promise that arbitrary application code can be forcibly interrupted safely.

Provide structured failure reporting, a minimal fallback diagnostic and optional logging integration. Applications choose error presentation; there is no mandatory fatal-error dialog. Reporting must not gate cleanup indefinitely or replace the originating failure if the reporting callback throws. Preserve reporting and cleanup failures as secondary diagnostics. The implementation must make the reporting lifetime and dispatch contract explicit; catching an exception alone does not contain an indefinitely blocking callback.

The #124 implementation uses a finite owner-work policy. A default reactive drain processes at most 10,000 posted completions and effects; a default lifecycle-context drain processes at most 1,024 callbacks. Explicit smaller limits remain available for tests and specialized hosts. An active drain is an implicit batch: `Batch`, `Drain` and `Composition.Flush` invoked by a running callback never recurse into another callback. Work they schedule remains in the same outer drain and consumes its existing budget. Callback failures are retained up to a fixed diagnostic cap, including the first failure, then summarized so a nonsettling write-then-throw effect cannot grow memory without bound.

Fatal abort logically cancels the current close-preparation generation and begins irreversible shutdown immediately. `PrepareCloseAsync` has no authority to publish after its generation is cancelled. Its task remains observed so a late fault is reported, but its late result does not change terminal status or the terminal failure returned to the caller. This cancellation does not cancel accepted application writes: `StopAsync` and lifecycle disposal still run to completion or surface their own failure, without a framework timeout.

Cancellation is cooperative. Lucent requests it before terminal cleanup and observes an asynchronous cancellation callback failure without awaiting it. Application preparation that ignores the token may remain incomplete. Preparation that depends on posting its cancellation continuation back to the owner context may also remain incomplete after that context closes; Lucent cannot force arbitrary application code to finish and does not delay shutdown to keep the context alive.

Applications may install a structured failure reporter on the application builder. Terminal and late-preparation reports are dispatched through independent thread-pool work after the corresponding failure is captured. Reporting therefore cannot delay service stop, composition disposal, lifecycle disposal or the exception returned by `Run`. A blocking reporter occupies only its reporting work item. A reporter exception and the original failure are written through the minimal fallback diagnostic; reporting cannot replace or mutate the application failure. The reporter must copy anything it needs. Its callback runs after cleanup, has no guaranteed access to UI or application services, and is best effort if the process exits immediately after `Run` returns.

## Microsoft container boundaries

Microsoft's DI container owns service disposal. Its asynchronous disposal can continue on a worker thread and stops within a scope if a disposer throws. Therefore UI-affine resources and subscriptions belong to Lucent composition scopes, and DI service disposal must be thread-independent and release its own resources reliably. Perform fallible persistence/service work in preparation or `StopAsync`, not in a destructor-like disposal path. Lucent always attempts its independent composition, application-scope and host cleanup boundaries and preserves their errors; it does not replace the container or claim to resume disposal inside a failed third-party provider.

[Generic Host](https://learn.microsoft.com/dotnet/core/extensions/generic-host), [DI guidelines](https://learn.microsoft.com/dotnet/core/extensions/dependency-injection/guidelines), and the [Microsoft container implementation](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/Microsoft.Extensions.DependencyInjection/src/ServiceLookup/ServiceProviderEngineScope.cs) inform this boundary. The adopted 10.0.11 packages are recorded in `CREDITS.md`. Factory registrations and statically reachable types are preferred for NativeAOT; typed configuration binding should use Microsoft's source generator. Default configuration-file loading, reflection scanning, logging sinks and per-element dependency injection are not implicit framework behavior.
