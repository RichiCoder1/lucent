# Style-driven layout with retained containers

Accepted September 8, 2026. Layout containers retain their children while styles select the arrangement strategy, child placement and responsive participation. Parameterized `.lui` styles and explicit reactive condition groups make these decisions reusable without moving them into application view models. Composition conditions remain appropriate for actual content ownership changes, and interactive state such as the selected route or preferred pane extent remains behavior-owned.

The framework exposes a bounded nonvirtualizing strategy interface over its managed projection, extending the internal-only decision in ADR 0004 without replacing the engine. Strategy implementations receive measurement and placement capabilities, not mutable composition or platform objects. Per-container scratch state cannot leak between mounts; measurement requests and output geometry are validated. Virtualization continues to use a separate realization contract so an ordinary custom strategy cannot accidentally enumerate or mount an entire data source.

The initial responsive surface uses named window breakpoints, assigned from the logical window viewport before layout. The reader is explicit and its source does not depend on where it is attached. Container queries and their containment/ancestor-lookup rules are deferred. Existing assigned-container readers and finite feedback diagnostics remain compatible, but the proving consumers use window breakpoints. Conditions use reactive dependency tracking, short-circuit when inactive, and preserve existing interaction-variant precedence. Width changes inside an unchanged predicate range must not rematerialize styles or remount components.

SwiftUI's interchangeable layouts and typed child values, WinUI's separation of layout/context/container, and Compose's constrained measurement and parent-data interfaces are architectural references recorded in CREDITS.md. Lucent retains its typed style model, `.lui` source maps, owner-thread execution and NativeAOT compatibility; no framework dependency or source is imported.

## Diagnostics and algorithm lifetime (September 9, 2026; #118)

Custom algorithm failures identify both the algorithm and the container's diagnostic name and element identity. Invalid results and measurement-limit violations follow the same path as exceptions thrown by the callback: an `InvalidOperationException` adds ownership context and retains the original exception as `InnerException`. The invocation context always expires, including on failure; captured children cannot be measured or inspected afterward.

`ReactiveGraph.Dump()` marks window breakpoint scopes as unregistered, mounted awaiting a viewport, or mounted with a viewport assigned. This is diagnostic metadata, not a warning or reactive application value. Construction before mounting is valid and retains the width-zero initial state; mounting does not invent geometry. A forgotten `breakpoints:` attachment remains discoverable in a dump, while an unmounted reader retains its last assigned width until disposed or remounted.

Algorithm state remains activation-owned. Switching algorithms releases the previous algorithm's resources when the container next participates in layout; disposing the container releases them immediately. A collapsed container is not laid out, so changing its Algorithm while collapsed defers that cleanup until participation resumes or the container unmounts. This retains the existing bounded lifetime without adding a reactive subscription per layout container. It does not remount the component or reset component-local state. Do not put resources requiring immediate cancellation on a style change into algorithm scratch state; use an explicit component-owned lifetime for those resources.

A virtualized viewport contributes no intrinsic source extent. Its own authored size and decoration can still contribute geometry, but the thousands of virtual rows are not measured to size an ancestor. A custom algorithm must assign its viewport dimensions, for example `new LayoutChildPlacement(index, new LayoutRect(0, 0, width, height))`, using bounded available dimensions or an explicit fallback. The `CustomAlgorithmAssignsViewportWithoutMeasuringEntireVirtualSource` contract demonstrates this with a 10,000-row source and an assigned 100 by 40 viewport. General layout algorithms remain nonvirtualizing; realization belongs to the viewport.
